# 工程师实施指南

## 1. 交付目标

建立一条可以复现和检查的运行优化流程：输入设备参数与多能时序数据，训练 PPO/SAC，输出逐时设备计划以及经济性、能源平衡、约束和运行时间指标。第一阶段以离线仿真与算法评估为交付目标。

建议能源工程师负责设备模型和业务口径，数据工程师负责数据接口与时序质量，算法工程师负责环境训练与评价；人员可合并，但每个口径需要有明确负责人。

## 2. 按什么顺序实施

| 步骤 | 具体工作 | 交付物 | 验收依据 |
|---|---|---|---|
| 1. 确认业务边界 | 明确园区设备、控制周期、费用项和硬约束 | 模型边界表、参数表 | 能源工程师确认功率和能量口径 |
| 2. 本地复现 | 跑规则控制、测试和运行图 | 环境版本记录、测试结果 | README 命令可执行，能量账目无误 |
| 3. 接入数据 | 转成统一 CSV，按时间划分数据集 | 数据字典、处理日志、划分表 | 缺失、重复、单位及未来信息审查通过 |
| 4. 校准仿真 | 核对效率、容量、爬坡和补足规则 | 校准后的配置和手算样例 | 关键工况与手算 / 独立模型一致 |
| 5. 验证 RL 接口 | 检查观测动作、终止语义与记录项 | 环境检查记录 | `check_env` 通过，动作修正可追溯 |
| 6. 短训练贯通 | PPO、SAC 各跑小步数，保存再加载 | 日志、模型、测试输出 | 两条训练—加载—评估链路可运行 |
| 7. 正式实验 | 验证集调参，多种子、同场景比较 | 指标表、训练曲线、典型日图 | 费用与可行性同时评估，不以训练奖励替代 |
| 8. 加入求解器基准 | 构建 MILP / MPC 并统一比较口径 | 基准模型、求解状态、时间记录 | 目标、信息、初末状态和约束可比 |
| 9. 接近真实运行 | 加入预测误差、故障、联合约束处理 | 扰动实验和回退记录 | 业务要求的异常工况均有明确处理 |

## 3. 第一个工作日怎么做

先按 README 完成安装和规则策略评估，打开 `dispatch.csv` 检查一个小时：电网购电如何得到、锅炉燃气是否与供热对应、热泵耗电是否只算一次、储能正负方向是否正确。再用 `tests/test_physics.py` 中的手算工况核对 92.06 CNY 单步费用。

读懂这一个小时之后，再检查 24 小时的储能动态与期末能量。最后接入 PPO；当训练结果异常时，优先检查环境和奖励分项，而不是直接增加网络层数。

## 4. 模块之间的接口

| 模块 | 输入 | 输出 | 修改原则 |
|---|---|---|---|
| 数据层 | 原始数据、时间字段 | 24 小时 DataFrame 列表 | 单位、时间和可获得性在这一层明确 |
| 配置层 | JSON | 不可变 `Config` | 新参数说明单位与范围 |
| 仿真层 | 当日数据、配置、动作 | 下一观测、奖励、终止、诊断字典 | 能源计算集中在 `core.py` |
| RL 适配层 | 数据列表、配置 | Gymnasium Env | 不复制一套能源方程 |
| 训练层 | 环境、算法、随机种子 | 模型、日志和验证结果 | 不读取测试数据 |
| 评估层 | 冻结策略、独立测试日 | 逐时表、每日表、汇总表 | 所有算法使用一致的物理结算 |

要添加一个新设备，需同步检查五处：配置、物理转移、观测 / 动作、成本与诊断字段、验证案例。若仅改变规则控制，不应修改物理环境来偏袒某个策略。

## 5. 如何替换为你的综合能源系统

例如实际园区没有吸收式制冷机，可先在规则中保持该动作取 -1；若要正式训练无 AC 场景，应移除该动作、修改空间维度和观察版本，并重新训练。当前配置验证要求动作映射相关容量为正，不宜只把容量改成零来删除设备。

如果要增加电锅炉，可增加其额定功率和效率，在电平衡右侧加入耗电、热平衡左侧加入供热，再确定它是策略控制还是残差补足。若增加可控负荷，必须增加舒适度、延期或服务约束，防止智能体通过不服务负荷降低账面费用。

如果设备存在启停，不能把连续动作简单取整就视为完成机组组合。需要加入启停状态、最小出力、启停时间及相应奖励 / 约束，并选择能表达离散—连续动作的策略结构。

## 6. 训练异常如何定位

| 现象 | 优先检查 | 下一步 |
|---|---|---|
| 奖励持续很差 | 缺口惩罚是否占主导、设备是否够用 | 先运行规则和独立可行性检查 |
| 回报提高但费用没降 | 是否只降低了期末惩罚或弃能 | 分开画费用、缺口、期末偏差 |
| SOC 长期顶格或见底 | 电价、充放方向和期末目标 | 检查能量方程及期末敏感性 |
| 动作经常被修正 | 设备边界是否过紧、探索是否过大 | 检查修正频率；再考虑联合可行域机制 |
| 学习曲线好、测试表现差 | 时序泄漏、过拟合或场景覆盖不足 | 检查划分、增加验证场景与训练种子 |
| 运行费用异常低 | 是否欠供能或耗尽储能 | 先排除不可行性和期末不公平 |
| 加载后行为不同 | 配置、观测顺序、随机策略差异 | 读取原配置，确定性预测，核对数据摘要 |

## 7. 求解器基准该怎么加

混合整数线性规划（Mixed-Integer Linear Programming，MILP）可以作为该固定效率模型的优化基准。建议新增 `baselines/milp.py`，输入与当前环境相同的数据和配置，输出相同单位的设备计划。储能充放互斥、购售互斥和可能的设备启停通过二进制变量表达；绝对值期末惩罚用辅助变量线性化。

求解器控制全部设备时比当前 RL 的“5 个动作 + 自动补足”具有更大的调度自由度。可以将其用作理想参考，但不能把全部差距解释为 RL 算法不足。若要求控制空间完全一致，需要明确实施相同补足关系，或升级 RL 为同等设备自由度。

若 MILP 使用整天真实未来数据，其结果是完美预知条件的参考费用；只有求解器返回经过证明的最优解且目标一致时，才可以称为该优化模型的最优参考。模型预测控制（Model Predictive Control，MPC）应使用决策时可获得的预测，滚动执行第一步，再与拥有同等信息的 RL 比较。

## 8. 从仿真到现场的接口设计

后续现场链路应区分状态采集、策略建议、约束检查和控制执行。至少记录输入时间戳、模型版本、建议动作、修正动作、执行确认和告警。数据过期、模型异常、设备不可用或联合约束不可行时，调用经过业务验证的备用控制。

本仓库没有写入现场设备的接口，也未完成硬件在环或现场试运行。上述内容是扩展任务，应在有真实数据和设备边界后实施；不能因为仿真中的 SOC 不越限就认为已完成现场安全验证。
